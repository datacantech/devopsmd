### **Docker: от простого к сложному и сравнение с другими CRI (containerd, CRI-O)**  

---

## **🔹 1. Что такое Docker? (Простое объяснение)**  
**Docker** — это платформа для **контейнеризации** приложений.  
- **Контейнер** — это "легковесная виртуальная машина", которая содержит приложение и все его зависимости.  
- **Пример:**  
  - Вы упаковываете веб-сервер (Nginx), базу данных (PostgreSQL) и код приложения в контейнеры.  
  - Эти контейнеры работают **изолированно** и могут быть запущены на любом компьютере с Docker.  

### **🔹 2. Как работает Docker? (Базовый уровень)**  
1. **Dockerfile** — инструкция для сборки контейнера.  
   ```dockerfile
   FROM ubuntu:22.04
   RUN apt update && apt install -y nginx
   CMD ["nginx", "-g", "daemon off;"]
   ```  
2. **Сборка образа** (`docker build -t my-nginx .`).  
3. **Запуск контейнера** (`docker run -d -p 80:80 my-nginx`).  

### **🔹 3. Архитектура Docker (Продвинутый уровень)**  
Docker состоит из:  
- **Docker Daemon** (`dockerd`) — управляет контейнерами.  
- **Docker Client** (`docker`) — CLI для взаимодействия с демоном.  
- **Docker Images** — шаблоны для контейнеров (хранятся в Docker Hub).  
- **Containers** — работающие экземпляры образов.  

---

## **🔹 4. Docker vs. Другие CRI (Container Runtime Interface)**  
CRI — стандарт Kubernetes для работы с контейнерами.  

### **🔹 4.1. Docker vs. containerd**  
| **Критерий**       | **Docker**                          | **containerd**                     |  
|--------------------|------------------------------------|-----------------------------------|  
| **Уровень**        | Высокоуровневая платформа          | Низкоуровневый рантайм            |  
| **Зависимости**    | Включает containerd, CLI, API      | Только рантайм (без Docker CLI)   |  
| **Использование**  | Для разработки и продакшена        | Для Kubernetes и embedded-систем  |  
| **Пример**         | `docker run nginx`                 | `ctr run docker.io/nginx nginx`   |  

**Разница:**  
- Docker использует **containerd под капотом**.  
- Kubernetes с версии 1.24 **перестал поддерживать Docker** и перешел на containerd/CRI-O.  

### **🔹 4.2. Docker vs. CRI-O**  
| **Критерий**       | **Docker**                          | **CRI-O**                         |  
|--------------------|------------------------------------|-----------------------------------|  
| **Назначение**     | Универсальные контейнеры           | Только для Kubernetes             |  
| **Размер**         | Больше (много компонентов)         | Минималистичный                  |  
| **Безопасность**   | Поддержка AppArmor, SELinux        | Оптимизирован под K8s (OCI-совместимый) |  
| **Пример**         | `docker ps`                        | `crictl ps` (аналог для CRI-O)   |  

**Разница:**  
- **CRI-O** создан специально для Kubernetes и не включает лишних компонентов.  

---

## **🔹 5. Когда что использовать?**  
1. **Docker** — если нужно:  
   - Локально разрабатывать и тестировать контейнеры.  
   - Использовать Docker Compose для оркестрации.  
2. **containerd** — если:  
   - Нужен легковесный рантайм для Kubernetes.  
   - Не требуется Docker CLI.  
3. **CRI-O** — если:  
   - Работаете **только с Kubernetes**.  
   - Важна минималистичность и безопасность.  

---

## **🔹 6. Примеры команд**  
### **Docker**  
```bash
docker build -t my-app .          # Собрать образ
docker run -d -p 8080:80 my-app   # Запустить контейнер
docker ps                         # Список контейнеров
```

### **containerd**  
```bash
ctr images pull docker.io/nginx   # Загрузить образ
ctr run docker.io/nginx nginx     # Запустить контейнер
```

### **CRI-O**  
```bash
crictl pull nginx                 # Загрузить образ
crictl runp nginx                 # Запустить под (аналог контейнера)
```

---

## **🔹 7. Вывод**  
1. **Docker** — самый дружелюбный инструмент для разработчиков.  
2. **containerd** — "движок" Docker, который Kubernetes использует по умолчанию.  
3. **CRI-O** — легковесная альтернатива для Kubernetes.  

**Совет:**  
- Для локальной разработки — **Docker**.  
- Для продакшена в Kubernetes — **containerd/CRI-O**.


### **Docker vs Podman: сравнение**  

#### **🔹 1. Общее описание**  
| **Критерий**       | **Docker**                          | **Podman**                        |  
|--------------------|------------------------------------|----------------------------------|  
| **Тип**            | Клиент-серверная архитектура       | Децентрализованный (без демона)  |  
| **Демон**          | `dockerd` (обязателен)             | Нет (работает без демона)        |  
| **Root-права**     | Требует root (или группу `docker`) | Может работать без root (`rootless`) |  
| **Поддержка Pods** | Нет (только контейнеры)            | Да (аналогично Kubernetes)       |  
| **Оркестрация**    | Docker Swarm (устаревает)          | Поддержка Kubernetes (K8s)       |  
| **Совместимость**  | Собственный API                    | Совместим с Docker CLI (`alias docker=podman`) |  

---

#### **🔹 2. Ключевые отличия**  

### **1. Архитектура**  
- **Docker** использует клиент-серверную модель:  
  - CLI (`docker`) → Демон (`dockerd`) → Контейнеры.  
  - **Проблема:** Если демон упал, контейнеры не управляются.  

- **Podman** работает без демона:  
  - CLI (`podman`) напрямую вызывает `runc` (или `crun`).  
  - **Преимущество:** Более безопасно и стабильно.  

### **2. Безопасность (Rootless-режим)**  
- **Docker**:  
  - По умолчанию требует **root** (или добавление пользователя в группу `docker`, что небезопасно).  
- **Podman**:  
  - Полноценная работа **без root-прав** (использует `namespaces` и `cgroups v2`).  
  - Пример:  
    ```bash
    podman run --rm -it alpine sh  # Запуск от обычного пользователя
    ```

### **3. Поддержка Pod (как в Kubernetes)**  
- **Docker**:  
  - Нет встроенной концепции **Pod** (группы контейнеров).  
- **Podman**:  
  - Может создавать **Pods** (как в Kubernetes):  
    ```bash
    podman pod create --name mypod
    podman run --pod mypod -d nginx
    podman run --pod mypod -d redis
    ```

### **4. Совместимость с Docker**  
- **Podman** поддерживает почти все команды Docker:  
  ```bash
  alias docker=podman  # Можно использовать как замену Docker
  ```  
- Но:  
  - Нет `docker swarm`.  
  - Нет поддержки Docker API (важно для некоторых инструментов, например, Portainer).  

### **5. Хранение образов**  
- **Docker**:  
  - Локальные образы хранятся в `/var/lib/docker` (требует root).  
- **Podman**:  
  - Хранит данные в домашней директории (`~/.local/share/containers`).  

---

#### **🔹 3. Производительность**  
- **Podman** немного медленнее при первом запуске (из-за отсутствия демона), но в целом сравним с Docker.  
- **Docker** быстрее в некоторых сценариях (например, при частых операциях с сетью).  

---

#### **🔹 4. Интеграция с Kubernetes**  
- **Docker**:  
  - Требуется `docker-shim` (устарел, в новых версиях K8s не поддерживается).  
- **Podman**:  
  - Лучше совместим с Kubernetes (можно создавать Pods и экспортировать манифесты):  
    ```bash
    podman generate kube mypod > pod.yaml  # Генерация манифеста K8s
    ```

---

#### **🔹 5. Когда что использовать?**  
| **Сценарий**                | **Docker**                     | **Podman**                     |  
|----------------------------|-------------------------------|-------------------------------|  
| **Локальная разработка**   | Да (удобный интерфейс)        | Да (лучше для rootless)       |  
| **Продакшн-серверы**       | Да (но требует настройки)      | Да (безопаснее)               |  
| **Kubernetes**             | Нет (устаревшая поддержка)     | Да (поддержка Pods)           |  
| **CI/CD (Jenkins, GitLab)**| Да (но требует демона)         | Да (легковеснее)              |  

---

#### **🔹 6. Примеры команд**  
### **Docker**  
```bash
docker build -t myapp .           # Сборка образа
docker run -d -p 8080:80 myapp    # Запуск контейнера
docker-compose up                 # Запуск через compose
```

### **Podman**  
```bash
podman build -t myapp .           # Сборка образа
podman run -d -p 8080:80 myapp    # Запуск контейнера
podman-compose up                 # Аналог docker-compose (не нативно)
```

---

### **🔹 7. Вывод**  
- **Выберите Docker, если:**  
  - Нужен проверенный инструмент с большим комьюнити.  
  - Используете Docker Swarm (хотя он устаревает).  
  - Работаете с инструментами, которые требуют Docker API (Portainer).  

- **Выберите Podman, если:**  
  - Нужна работа **без root** (безопасность).  
  - Хотите использовать **Pods** (как в Kubernetes).  
  - Не хотите зависеть от демона.  

**Совет:** Попробуйте `podman` с `alias docker=podman` — многие даже не заметят разницы!  

--- 

📌 **Итоговая таблица:**  

| **Функция**         | **Docker**      | **Podman**     |  
|---------------------|----------------|----------------|  
| **Демон**           | Да (`dockerd`) | Нет            |  
| **Rootless**        | Нет (требует настройки) | Да (из коробки) |  
| **Pods**            | Нет            | Да             |  
| **Kubernetes-совместимость** | Нет (с v1.24+) | Да             |  
| **Производительность** | Быстрее (с демоном) | Легковеснее (без демона) |  
| **CLI-совместимость** | Свой синтаксис | Почти полная совместимость с Docker CLI |  

Если вам нужна **максимальная безопасность** и интеграция с **Kubernetes** — выбирайте Podman.  
Если важна **поддержка старого ПО** и **Docker Swarm** — пока лучше Docker.
